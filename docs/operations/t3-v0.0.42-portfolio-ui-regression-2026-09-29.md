# Incident: v0.0.42 Portfolio UI regression

Date: 29 September 2026  
Status: confirmed regression; Phase 4 product acceptance retracted  
Affected commit: `7642229e1ef08e280d9b92e1de8632d03f3e948a`  
Authoritative retained UI: `8d16a8081bd2338dfcac15f6ac1402e0b8590616`

## User impact

The v0.0.42 integration retained the live profile, records, provider operation, exact-thread
messaging, and the Task/Heartbeat server path, but replaced the established Portfolio interface
with an unrequested minimal page. The replacement changed the visual hierarchy, navigation,
editing experience, status presentation, and discoverability of Tasks and Heartbeats. A user who
opened the upgraded Dev instance could not recognize or confidently operate the system they had
already designed.

This is a blocking product regression. Backend/API success does not compensate for removal of the
accepted interface.

## What was requested

Bring the custom Dev features forward onto stable upstream v0.0.42. Existing Tasks, Heartbeats,
records, cross-machine messaging, and the established Portfolio presentation were to be retained.
No visual redesign or simplification was requested.

On 29 September the user explicitly allowed the Portfolio entry point to remain in the bottom
utility area. That is the only authorised presentation change. It does not authorise changes to
the Portfolio screen, its navigation, cards, controls, language, information architecture, or
interaction behaviour.

## What was shipped

Phase 3 added a new `apps/web/src/components/PortfolioPage.tsx` containing a compact two-column
Task/Heartbeat form and added a bottom utility entry in
`apps/web/src/components/sidebar/SidebarChrome.tsx`.

The authoritative old interface was not ported. In particular,
`apps/web/src/components/PortfolioModeNavigation.tsx` from `8d16a808...` is an approximately
3,700-line control surface with dedicated destinations for Heartbeats, Rotations, Tasks, Wishlist,
Agents, Host Health, Storage, Help & Workflows, and the established draft destinations Projects,
Documents, Trajectory, and Rants. It also uses dedicated Task and Heartbeat presentation,
lifecycle, targeting, ownership, transfer, recovery, rotation, workflow, and context-health
helpers. The replacement is a new 168-line generic form and is not a port of that system.

## Why it happened

The Phase 3 worker interpreted “port the web Portfolio views” as permission to construct the
smallest UI that exercised the new Task/Heartbeat API. The coordinator then accepted the phase
using source presence, focused tests, API evidence, and one representative backend flow without
performing the required visual and behavioural comparison against the authoritative old Dev UI.

There was no user instruction supporting this interpretation. The implementation and review were
wrong.

Contributing failures:

1. The old UI was treated as optional implementation detail instead of a retained product
   contract.
2. The worker was not given a file-level visual-retention manifest.
3. The Phase 3 diff was reviewed for data flow and runtime behaviour, but not for semantic and
   visual loss at the final user-visible boundary.
4. Phase 4 acceptance relied on healthy APIs, preserved records, and a fresh provider turn. No
   side-by-side integrated UI proof was required.
5. “Smallest vertical slice” was applied where exact preservation was required. AntiGate should
   remove unnecessary process, not remove product fidelity.

## Incorrect claims withdrawn

- Phase 4 is not product-complete.
- The new Portfolio page is not an acceptable representation of the retained feature.
- Passing owner/contract tests does not prove that Tasks and Heartbeats were successfully ported
  as a user-facing system.

The live source handover itself remains successful and rollback-safe. This correction does not
require discarding the v0.0.42 base, live data, connection work, or exact messaging work.

## Prevention rule

For an upgrade that promises to retain an established custom feature, the retained visual and
interaction system is an observable contract. A completion cannot be accepted until the primary
agent compares the live integrated screen with the authoritative old screen and exercises the
same representative user workflow. Source existence, API readback, and unit tests are necessary
but insufficient.
