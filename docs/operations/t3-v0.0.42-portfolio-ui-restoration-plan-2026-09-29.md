# Exact Portfolio UI restoration on v0.0.42

Date: 29 September 2026  
Status: authoritative corrective implementation plan  
Old visual/behavioural reference: `8d16a8081bd2338dfcac15f6ac1402e0b8590616`  
Current v0.0.42 integration branch: `sned/t3-dev-v0.0.42-integration`

## Outcome

Restore the established custom Portfolio experience on the v0.0.42-based live Dev runtime. Keep
the upstream v0.0.42 connection/provider foundation and the new server-owned Task/Heartbeat
runtime, but make the visible Portfolio system match the old Dev design and behaviour. Do not
invent a third design.

## Anti-regression contract

**Retain**

- The established Portfolio visual language, spacing, hierarchy, cards, labels, status treatment,
  detail views, empty states, and interaction flow from `8d16a808...`.
- Portfolio destinations: Heartbeats, Rotations, Tasks, Wishlist, Agents, Host Health, Storage,
  Help & Workflows, plus the existing draft Projects, Documents, Trajectory, and Rants entries.
- Task cards/detail, assigned agent and environment presentation, checklist/evidence progress,
  status, timestamps, completion condition, linked documents, receipts, and stable identity.
- Heartbeat current/cards views, linked or standalone presentation, custom message and fallback,
  cadence, next run, run count, lifecycle, On/Off behaviour, owner state, transfer presentation,
  receipts, stop conditions, and exact target identity.
- Rotations, Wishlist, Agents/native messaging, host inventory, storage, workflow help, recovery,
  and context-health presentation that already exists in the old Portfolio surface.
- All 19 live Tasks, existing thread history, `.t3-dev`, exact-thread messaging, remote
  environments, the existing scheduled-task lifecycle, and the source/state rollback.
- Web performance and v0.0.42 remote-ready behaviour.

**Add or repair**

- Adapt the old presentation and interactions to the v0.0.42 client/runtime boundaries.
- Restore any Task/Heartbeat contract fields and operations that the minimal Phase 3 port dropped
  but the established interface requires.
- Add focused regression coverage for the adapter boundary and one integrated UI workflow.

**Replace**

- The old top-level Portfolio entry location may be replaced by the v0.0.42 bottom utility entry;
  the user explicitly accepted this placement on 29 September.
- Nothing else is authorised for visual or behavioural replacement.

**Affected boundaries**

Old presentation -> v0.0.42 route/shell -> web view model -> client-runtime commands -> current
server owner/scheduler -> preserved live records and native turn receipts.

**Direct evidence**

One side-by-side live comparison at a fixed desktop viewport, followed by one real retained Task
edit and one Heartbeat lifecycle operation through the restored interface. API-only proof is not
acceptance.

## Precise implementation sequence

### 1. Capture the retained visual contract

Run the rollback source only in an isolated profile and separate ports. Capture the established
Portfolio sidebar, each implemented destination, Tasks list/detail/edit states, Heartbeat
current/cards/detail/edit states, empty/error states, and desktop responsive behaviour. Do not
point it at `.t3-dev` and do not replace the live owner.

Record the visible labels, ordering, controls, default selection, spacing, card structure, and
state transitions. These screenshots and the old source are the review reference; memory or a
new mock-up is not.

### 2. Restore the old Portfolio shell inside the v0.0.42 route

Keep `/portfolio` and the accepted bottom utility button. Replace the minimal
`PortfolioPage.tsx` content with a v0.0.42-compatible composition of the old:

- Portfolio destination sidebar;
- Portfolio top bar;
- Portfolio destination view.

If v0.0.42 no longer permits the old global `AppSidebarLayout` mode swap cleanly, render the old
Portfolio sidebar as the left pane inside `/portfolio`. Preserve its width, styling, destination
ordering, active treatment, and responsive behaviour. Do not redesign it to resemble the generic
v0.0.42 Settings sidebar.

### 3. Add a compatibility adapter, not a replacement UI

Keep presentation components close to their old source. Put unavoidable runtime-shape conversion
at a named adapter boundary. Required mappings include:

| Established UI meaning | Current runtime representation | Required rule |
|---|---|---|
| Task assignment | flat `ownerPassportId` / `ownerHost` | expose the old `assignment` view shape without changing identity |
| Checklist author | old `updatedBy` | restore/preserve the field where stored; do not silently erase it on write |
| Primary document link | old `primary` | retain the established indication and persistence semantics |
| Task edits | current revision-checked complete write | expose separate edit/status actions in the old UI and preserve immutable target/ID |
| Task lifecycle | current Task status | preserve old labels, transitions, completed timestamp, and linked Heartbeat shutoff |
| Heartbeat lifecycle | current status/owner scheduler | present the established On/Off and lifecycle language while keeping one scheduler |
| Heartbeat receipt | current `lastReceipt` | render the old receipt/status presentation without fabricating confirmation |
| Exact target | current environment/project/thread tuple | retain human labels and never infer or replace IDs |

When an old UI capability has no current runtime operation, restore the missing operation at the
existing contract/client/server boundary. Do not hide the control, replace it with a generic
field, or add a browser-owned scheduler as a shortcut.

### 4. Restore each destination cumulatively

Restore in this order so every checkpoint remains usable:

1. Portfolio shell and navigation.
2. Tasks list, cards, detail, edit, checklist/evidence, status, links, and receipts.
3. Heartbeat current/cards views, detail/edit, lifecycle, linkage, ownership, transfer, and
   receipts.
4. Rotations and context-health/recovery views.
5. Wishlist.
6. Agents/native messaging, Host Health, Storage, Help & Workflows.
7. Existing draft destinations with their original draft treatment.

Each step retains the completed previous steps. A generic placeholder is not completion for an
implemented old destination.

### 5. Focused verification

Use focused tests only:

- presentation helper tests carried from the old commit;
- adapter tests for assignment, checklist author, documents, lifecycle, receipt, and target
  preservation;
- current owner/scheduler tests for the operations exercised by the UI;
- a web test that asserts the exact destination set/order and the characteristic Task and
  Heartbeat card/detail controls.

Do not substitute a snapshot-only test for browser use.

### 6. Integrated acceptance before another completion claim

In an isolated v0.0.42 runtime seeded from a consistent snapshot of live state:

1. Compare the old and restored Portfolio screens side by side at the same viewport.
2. Open an existing Task, edit checklist evidence, save it, and confirm the same Task ID and target.
3. Open or create a bounded Heartbeat, verify its card/detail presentation, turn it On, observe one
   native exact-thread delivery and receipt, then turn it Off.
4. Visit every Portfolio destination and confirm implemented/draft states match the old UI.
5. Confirm Connections and provider operation remain upstream-current.

The user reviews the restored visual result before live acceptance. Only after that review may the
live owner be advanced. The old source checkout and rollback snapshot remain available throughout.
